# Exchange paper trading platform

This is an **incomplete prototype**, not a complete exchange. It supports limit-order matching, positions, basic P&L, reservations, mark-price updates, a persisted liquidation flow, concurrent order submission across markets, and a React dashboard.

With Docker running, start everything with `docker compose up --build`. Open the dashboard at **http://localhost:3000**; the exchange API is at `http://localhost:8080/api`. PostgreSQL persists in the `exchange-data` volume. The guided demos use a second backend and the separate `exchange-demo-data` volume. Java 21 is the target; `mvnw` and `mvnw.cmd` bootstrap Maven. Stop the services with `docker compose stop`.

For frontend development, with the Compose backends running, use `cd frontend`, `npm ci`, then `npm run dev`. Vite proxies the main API to port 8080 and the isolated demo API to localhost port 8081. Run `npm run check` and `npm run build` for the frontend checks.

The dashboard shows the selected market, order book, trade history, account balances and positions, open orders, and event timeline. It can submit or cancel orders and change the practice mark price. The scenario workspace provides guided liquidation and shared-collateral cases in a separate database. Loading a scenario resets **that scenario database**, not the main exchange. In the liquidation scenario, after the first buyer fills five contracts, optionally run `docker compose kill demo-backend` followed by `docker compose up -d demo-backend`, wait for the live connection to return, and then add the second buyer. Scenario progress is stored in the browser session; after a new browser session, reload the scenario to start again. The platform uses practice prices and virtual balances; no real funds are involved.

The `/api/stream` SSE endpoint polls the committed event timeline and sends refresh hints; it does not stream uncommitted changes. The dashboard fetches persisted state when the stream connects or reconnects and on each notification. A five-second refresh heartbeat also covers missed notifications and commits whose event IDs become visible out of order. The stream is a notification mechanism, not a durable replay log. Rejected requests are currently shown as dashboard errors but are not yet persisted in the event timeline.

The prototype uses integer cents and computes a reservation as `ceil(price_cents * quantity / 5)`. Position margin is 20% of entry notional, rounded up, and equity includes unrealized P&L at the current mark. Average entry is rounded to the nearest cent, with ties rounded up, each time a position is increased. Reductions realize `(fill price - entry price) * closed quantity` for longs, with the sign reversed for shorts; reversals open the remainder at the fill price. Matching uses resting price and price-time priority. Self-matches are skipped. The risk calculation is deliberately preliminary, and it is not a complete risk engine. The schema and API may change as the missing exchange features are implemented.

### Market concurrency and shared collateral

Each market has a dedicated single-threaded worker with a FIFO queue of up to 256 waiting commands. Order submission, cancellation, and mark updates enter the relevant queue; the HTTP response waits for the worker's database transaction to complete. A full queue or shutdown returns HTTP 503. Queues live only in memory: an interrupted client or backend crash can leave a command's outcome unknown, so submit retries must use the same client ID. Committed results live in PostgreSQL; uncommitted queued commands are not replayed automatically.

Normal order and cancellation transactions acquire a shared risk gate and a transaction-scoped advisory lock for their market. Transactions on different instruments can proceed together. Before matching, a transaction locks the incoming account and all potentially matching counterparty account rows in sorted account-ID order. The available collateral check and order reservation occur under the account lock. Cancellation uses the same market/account lock order. A client-ID lock prevents simultaneous use of the same key across markets. Matching serializes inside a market, but an unrelated account in another market does not need to wait for that market's account lock. These locks remain necessary alongside the in-process queues for cross-market account consistency and coordination with risk processing.

Mark updates and liquidation reconciliation take the risk gate exclusively because they may cancel orders and create liquidation orders across markets. Internal liquidation matching runs under this gate, rather than entering a market's external command queue; it cannot overlap normal market transactions and may run ahead of commands still waiting in memory. Reconciliation after a fill runs in a separate transaction after the fill commits. While reconciliation is pending, new orders from breached accounts are rejected and breached resting orders are cancelled instead of matched. A crash in that gap is recovered by the startup scan. A scheduled scan also retries every five seconds by default (`exchange.risk.retry-delay-ms`), skipping a cycle if it cannot immediately acquire the risk gate and retrying at the next interval. Thus a sustained workload can delay the scan. Before a risk-increasing fill, both accounts are checked again at the actual execution price under their account locks. An order whose full proposed fill would exceed collateral is cancelled; this prototype does not try a smaller fill to find an affordable quantity.

Run the isolated shared-collateral demo with `powershell -ExecutionPolicy Bypass -File scripts/collateral-demo.ps1`. Two `$350` orders compete for Alice's `$100`: one is accepted with `$70` reserved, and one is rejected. The script cancels the winner and submits a fresh order on the other market. The automated integration test uses a barrier to release both HTTP clients together and also checks that an unrelated market can make progress while Alice's row is locked. The script's two background jobs demonstrate the API outcome; the test provides the synchronization guarantee.

Read `/api/markets`, `/api/accounts`, `/api/orders`, `/api/positions`, `/api/fills`, `/api/liquidations`, and `/api/events` in a browser. POST orders as described in the controller's `OrderRequest`, and DELETE `/api/orders/{clientId}` to cancel an open order. Set a mark with `PUT /api/markets/BTC-PERP/mark` and JSON `{"priceCents":4500}`.

### Liquidation and recovery

Maintenance margin is the sum over positions of `ceil(abs(quantity) * mark_cents * 12 / 100)` cents. Equity is cash plus the sum of `quantity * (mark - entry)` in cents. If equity is strictly below maintenance, the exchange opens an episode, cancels the account's open ordinary orders, and creates a reduce-only order at the current mark. To keep this prototype conservative, it blocks **all** new orders during the episode, including orders that might reduce risk. Positions are handled by symbol in alphabetical order and the episode continues until all positions are flat, even if equity improves. Unfilled liquidation orders remain open at their original captured mark. The matching transaction caps each reduce-only fill at the current position and cancels any excess.

The mark change, breach detection, and order creation normally commit together. Startup scans persisted positions and episodes and creates any missing order. A fill, both position/cash changes, order quantities, reservations, and fill event commit together. A single active backend instance is assumed.

Run an isolated restart demonstration in PowerShell with `powershell -ExecutionPolicy Bypass -File scripts/recovery-demo.ps1`. It starts a temporary Compose project on port 18080, creates two practice buyer accounts, submits the scenario through REST, kills and starts the backend while leaving that project's PostgreSQL running, verifies the partial and final states, and removes the temporary project and volume. It does not touch the normal Compose volume. The manual equivalent for a running normal project is `docker compose kill backend` followed by `docker compose up -d backend`.

Integration tests normally use Testcontainers. If Docker's API is incompatible with the bundled Testcontainers version, set `TEST_DATABASE_URL` to a **dedicated disposable database** before `mvnw.cmd test`; the test suite truncates its tables and must never point at a database containing data you want to keep. The test fallback uses the `exchange` username and password. The original Windows Docker/Testcontainers connection issue is not yet resolved.
